# Operating model

This document explains how Agent Kernel should be used day to day. It is not a roadmap. It describes the current governance loop that keeps AI coding agents useful without letting them silently rewrite project standards.

Use this doc when you are onboarding a new project, connecting a new agent, reviewing a proposed memory, or deciding whether a repeated failure should become a durable rule, workflow, policy, or skill trigger.

---

## Mental model

Agent Kernel is a local governance layer between the user and coding agents.

```text
user intent
  -> agent work
  -> proposed memory or captured failure evidence
  -> user review
  -> approved source JSON
  -> compiled agent instructions
  -> safer future agent work
```

The important distinction is simple:

| Layer | Owns | Edited by |
|---|---|---|
| Source JSON | Durable rules, preferences, workflows, project notes, skills, policies, Failure Lessons | Agent Kernel commands |
| Proposal inbox | Suggested memory that needs review | Agents may create proposals, user approves or rejects |
| Episodes | Searchable history and decision notes | User or agent command with explicit intent |
| Generated outputs | `AGENTS.md`, `CLAUDE.md`, Cursor rules, Gemini files, Antigravity files | Generated by compile, sync, or link commands |
| Hooks | Narrow lifecycle adapters | Installed deliberately, kept auditable |
| MCP | Local tool access for agents | Read/search/propose by default, approval disabled by default |

Generated output is never the source of truth. If a generated file is wrong, change the source memory or protocol, then compile and link again.

## Daily workflow

### 1. Start the project with current memory

```bash
agent-kernel doctor
agent-kernel sync
agent-kernel-safe-link . --dry-run
agent-kernel-safe-link .
```

Use `--dry-run` first when the project already has hand-written agent files.

### 2. Let agents work from generated guidance

Agents should read the relevant file for their surface:

| Agent | Primary file or surface |
|---|---|
| Claude Code | `CLAUDE.md`, `AGENTS.md`, MCP, hooks |
| Codex | `AGENTS.md`, `.codex/AGENTS.md`, `.codex/config.toml` |
| Cursor | `.cursor/rules/00-agent-kernel.mdc` |
| OpenCode | `AGENTS.md` |
| Antigravity | `.agents/agents.md`, `.agents/skills/README.md` |
| Gemini CLI | `GEMINI.md` |

### 3. Capture lessons when work fails

Before retrying a familiar error, search Failure Lessons:

```bash
agent-kernel failure search "ERR_MODULE_NOT_FOUND"
```

When a failure produces a reusable fix path, capture it:

```bash
agent-kernel failure capture \
  --from claude \
  --type test-failure \
  --command "npm test" \
  --exit-code 1 \
  --text "ERR_MODULE_NOT_FOUND ..." \
  --root-cause "Node ESM import path missed its explicit extension." \
  --fix "Add the explicit .js extension to the relative import."
```

### 4. Promote only what should become durable behavior

A Failure Lesson is evidence. It should become durable memory only when it is likely to repeat.

```bash
agent-kernel failure propose <failure-lesson-id> --as rule
agent-kernel inbox
agent-kernel approve <proposal-id> --publish
```

Allowed promotion targets are `rule`, `policy`, `workflow`, `skill`, and `note`.

### 5. Keep approval human-owned

Agents may suggest. Agents may capture. Agents may propose.

Agents should not silently approve, publish, or bypass the inbox.

## New project setup

Use this path for an existing codebase:

```bash
agent-kernel init --sync --enforce
agent-kernel compile
agent-kernel-safe-link . --dry-run
agent-kernel-safe-link .
agent-kernel-safe-git-hook . --dry-run
agent-kernel-safe-git-hook .
agent-kernel doctor
```

Why this order:

1. `init --sync --enforce` creates the home structure, compiles current memory, and installs enforcement where supported.
2. `compile` refreshes generated outputs before linking.
3. `agent-kernel-safe-link . --dry-run` shows exactly what will be created, appended, or replaced.
4. `agent-kernel-safe-link .` writes only marked Agent Kernel blocks into project files.
5. `agent-kernel-safe-git-hook` preserves existing pre-commit logic while adding guard behavior.
6. `doctor` catches missing setup or broken paths before agents depend on them.

Use the direct `agent-kernel link . --hooks` path only when you have decided the main CLI linker is the right behavior for that repository.

## Memory decision rules

Use this table when deciding where a piece of knowledge belongs.

| Knowledge type | Store as | Example |
|---|---|---|
| Hard policy | `policy` or critical rule | Never commit private MCP credentials |
| Working preference | `preference` | Use pnpm in this repository |
| Repeatable process | `workflow` | Run build before smoke tests |
| Project-specific context | `project-note` | This app uses Supabase auth and RLS |
| Repeated error with fix | Failure Lesson | ESM import needs explicit `.js` extension |
| Historical decision or session summary | Episode | Why the SQLite fallback was removed |
| Tool routing trigger | `skill` | If user asks for docs audit, inspect docs map first |

A useful test: if the agent should remember it next month, it probably belongs in source memory. If it mainly explains what happened in one session, it probably belongs in an episode.

## Failure Lessons loop

Failure Lessons are the error-to-skill path.

```text
failure happens
  -> capture command, exit code, error text, root cause, fix
  -> dedupe by project + command + error signature
  -> search before retry next time
  -> promote recurring lessons into approved memory
```

A good Failure Lesson has five properties:

1. It names the failing command or operation.
2. It preserves enough error text for future matching.
3. It states the root cause, not just the symptom.
4. It gives the smallest known fix path.
5. It avoids over-generalizing from one project unless the pattern is truly reusable.

Bad lesson:

```text
Tests failed. Fix imports.
```

Good lesson:

```text
Command: npm test
Error signature: ERR_MODULE_NOT_FOUND
Root cause: Node ESM relative import missed explicit extension.
Fix: add the `.js` extension to the relative import path.
```

## Hook boundaries

Hooks are lifecycle adapters, not hidden agents.

Recommended boundaries:

| Hook use | Recommended event | Should it approve memory? |
|---|---|---|
| Block dangerous commands before execution | `PreToolUse` | No |
| Capture failed tool output | `PostToolUseFailure` | No |
| Add short context to a session | Session lifecycle event where supported | No |
| Scan files after writes | Narrow post-write event where supported | No |

Hook output should stay short, structured, and auditable. Prefer exec-form commands with `command` and `args`. Avoid broad matchers when the agent platform supports event-specific hooks.

## MCP trust model

The MCP server exposes local Agent Kernel state to agents over stdio.

Default intent:

- read status
- search memory
- propose memory
- inspect pending proposals
- run guard checks
- work with episodes where supported

Approval through MCP remains disabled by default. The safer workflow is still:

```text
agent proposes -> user reviews inbox -> user approves -> kernel publishes
```

Enable approval through MCP only for a trusted local workflow and only when the user explicitly wants that behavior.

## Contributor workflow

When changing runtime behavior:

1. Read `docs/ARCHITECTURE_NOW.md` before editing.
2. Edit `src/cli.mjs` for core runtime behavior or a focused `bin/` helper for standalone behavior.
3. Do not hand-edit `dist/cli.mjs`; run the build.
4. Update README, this doc, and the relevant protocol doc.
5. Add or update smoke coverage.
6. Run the full local gate:

```bash
npm run build && npm test && npm run lint && npm run typecheck
```

When changing only docs, still check that examples match the real package commands and current runtime surface.

---

## What not to do

- Do not treat `src/{adapters,commands,core,hooks}/` as active runtime modules yet.
- Do not edit generated guidance as if it were canonical.
- Do not let hooks approve memory.
- Do not store secrets in repo-local ECC files.
- Do not promote every failure into a rule. Capture first, promote only when the pattern is reusable.
- Do not replace existing project instructions with generated output unless that is the explicit intent.
